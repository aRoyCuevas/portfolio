Do the security tests notice when a defense is removed?

Case study: an accounts-receivable system for a retail store.

Summary. A green security test does not prove the defense it is named after. Removing one defense at a time, the security tests noticed 11 of 25 removals and the full suite 21 of 25; two new tests raised that to 23/25. A second system went from 15/28 to 28/28.

Who did what

  • I set the question, directed the work and made the decisions.
  • My AI agent environment ran the measurement: the mutation runner, the runs and the two new tests.
  • A second, separate AI session, which I commissioned, drafted the initial list of candidate mutants from the code and later reviewed the result. It worked from the code, the commit and the written report, not from the first session's conversation.

The question

An internal report listed the system's defenses, and a set of test files attacked them: the security tests. If one defense is removed, does any test fail?

Method

On a disposable copy with a green baseline, one mutant at a time (an exact text change removing one defense) ran against the security tests and full suite. A control mutant survived every run. 26 mutants, one equivalent: 25 defenses, any layer.

The two real gaps

  1. Row lock on sale confirmation. The concurrency test reused one idempotency key, so idempotency absorbed the second request and the test never exercised the lock. New test: parallel confirmations with different keys, one charge.
  2. Stale-totals check. No test covered it, and no API path can make it fire: it guards against a regression or a direct database edit. The test simulates that by editing the database, not an attacker's path.

Each new test fails with its mutant and passes without it. Two second-layer tenant filters still survive, since the outer layer already returns 404; I chose to document them rather than test them.

The correction from the second session

My environment first reported 19/19. The review found an uneven exclusion rule and an unmutated price layer. With one rule and four more mutants: 23/25, in a new commit.

A second system

A second system, in production use, went through the same measurement: the full suite noticed 15 of 28 removed defenses. The same pattern appeared: a negative test passed because input validation rejected the request before the check it was named after ever ran. No defense was missing; tests were. They have been added, and the suite now notices 28 of 28, with the control mutant still surviving. Here too, the same agent environment chose the mutants and wrote the tests.

Limits

  • The mutants were chosen by reading the code. The rate measures how many known defenses have a test, not how many unknown vulnerabilities the security tests would find.
  • The second session proposed the initial list of mutants and later reviewed the result, so it is not independent of the selection.
  • The application code, the tests and the mutation runs come from the same agent environment. The second session read the code, the commit and the report; it did not run anything.
  • The full suite ran against mutants only in UTC.
  • The concurrency test depends on the two requests overlapping. It cannot give a false red; it can give a false green.
  • The 6 frontend rows of the report (XSS, CSP, clickjacking) were not measured.
  • The two surviving second-layer filters still have no test of their own: if the outer layer is removed, nothing warns.
  • In one run, two security test files failed to load for one mutant. A repeat did not reproduce it and the cause was not determined; that mutant's result did not change.

What changes in practice

Reviews start from an inventory of every defense, found or not, and measure the tests by seeding faults into it. A green security test counts only once it fails without its defense.
